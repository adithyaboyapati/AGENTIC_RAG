2. System at a glance

Agentic RAG is a multi-mode research assistant. One question can be answered seven different ways — from a fixed retrieve→generate baseline up to a full orchestrator that chooses strategy, grades evidence, and may rewrite or fall back to the web. Every path shares the same retrieval stack, citations, guardrails, memory packing, and optional Redis cache.

3. Layered architecture

Think in five layers. Higher layers never bypass lower safety layers.

LayerResponsibilityPrimary modules
1. Interface HTTP, CLI, UI. Auth headers, SSE framing, session IDs. src/api/server.py, frontend/, src/cli.py, streamlit_app.py
2. Control plane Privacy, input/output guards, cost budgets, cache, memory packing. runner.py, guardrails.py, privacy.py, cache/, memory/
3. Agent graphs Mode-specific LangGraph StateGraphs (or baseline pipeline). src/graph/*, src/rag/baseline.py, src/agents/*
4. Knowledge plane Ingest, hybrid search, rerank, parent expansion, citations. src/ingestion/*, src/retrieval/*
5. Model & tools LLM client, structured outputs, tools, web search. src/llm.py, src/chains/, src/tools/
Hard rule
Never call ask_baseline, ask_crag, etc. from a new interface. Always go through run_agent() or stream_agent(). Skipping the runner skips privacy, rate/cost guards, cache, memory augmentation, and follow-ups.

4. End-to-end request lifecycle (every step)

This is the spine of the system. Below is the exact order of operations for a successful POST /query, then the streaming variant, then how CLI/Streamlit differ.

4.0 Master flow

Client → middleware (TrustedHost? → RequestId → CORS) → verify_api_key + enforce_client_rate_limit → (sync only) Idempotency-Key lookup → _resolve_chat_history (client history | Supabase | none) → concurrency semaphore → run_agent / stream_agent A. PrivacyGuard.apply_input B. InputGuardrails.validate C. should_use_cache? D. augment_question_with_history (if memory + history) E. cache hit? → post-guards → return F. CostGuardrails (QPM + token budgets) + record_query G. _dispatch(mode) → graph / baseline H. OutputGuardrails + PrivacyGuard.apply_output I. optional QualityGuardrails J. generate_follow_ups K. set_cached_response (if eligible) → _persist_exchange (Supabase, if session) → QueryResponse / SSE frames + metrics

4.1 FastAPI bootstrap

  1. Entry: uvicorn src.api.server:app (or python -m src.api.server).
  2. Import: import src.bootstrap initializes LangSmith env before LangChain imports.
  3. Lifespan: setup_logging(), init_langsmith_tracing(), deprecation warnings, and — if is_production() — _validate_production_config().
  4. Production refuse-to-start when: missing OPENAI_API_KEY; auth required but no API_KEY; CORS_ORIGINS=*; API_KEY shorter than 32 chars; API_WORKERS>1 with RATE_LIMIT_BACKEND=memory.

4.2 Middleware (order)

In Starlette, the last middleware added runs first on the request. Effective inbound order:

  1. TrustedHostMiddleware — only if TRUSTED_HOSTS is set.
  2. RequestIdMiddleware — accept or mint X-Request-ID, bind via set_request_id(), echo on response.
  3. CORSMiddleware — origins from CORS_ORIGINS; credentials only when origin is not *; methods GET|POST; headers include X-API-Key, Idempotency-Key.

4.4 Synchronous path — POST /query

  1. Dependencies: verify_api_key + enforce_client_rate_limit.
  2. Idempotency (optional): if Idempotency-Key present → get_idempotent_response. Body-hash mismatch → 409. Hit → return stored QueryResponse with metric status idempotent.
  3. History: _resolve_chat_history(session_id, use_memory, client_history) (see §5).
  4. Concurrency: acquire _query_semaphore (size max_concurrent_queries) within concurrency_acquire_timeout_seconds; else 503 + Retry-After: 5 + record_capacity_rejection().
  5. Execute: _run_agent_with_timeout = asyncio.to_thread(run_agent, …) + asyncio.wait_for(request_timeout_seconds).
  6. Persist: _persist_exchange(session_id, question, answer, mode) when memory + Supabase are active.
  7. Respond: build QueryResponse; store idempotent response if keyed; record_request(mode, "query", status, latency).
FailureHTTP
TimeoutError504
RateLimitError (process budget)429 + Retry-After 60
ValueError (guards / privacy block / bad mode)400
Unhandled500 (no internal detail leaked)
Gap
Idempotency applies only to /query, not /query/stream.

4.5 Streaming path — POST /query/stream

  1. Same auth + per-client rate limit (no idempotency).
  2. Resolve chat history.
  3. Spawn a worker thread that runs stream_agent(..., cancelled=threading.Event).
  4. Events are pushed onto an asyncio.Queue via loop.call_soon_threadsafe.
  5. Under the concurrency slot, pull events with dual timeouts:
    • Gap: request_timeout_seconds between events
    • Wall: stream_timeout_seconds total deadline
  6. On type==answer: capture text for later persist.
  7. On type==done: persist exchange; inject latency_ms + session_id; metric ok.
  8. Yield SSE frames: data: {json}\n\n.
  9. On error / timeout / client disconnect: cancelled.set(), cancel producer.
SSE typeMeaning
stepAgent/graph progress line (router decision, hop, grade, …)
tokenFinal-answer token as it generates
answerFull answer text (after generation / post-guards)
follow_upsList of follow-up questions
sourcesSource labels + citations array
doneTerminal frame: latency, session, mode, route, steps; may include cached: true
errorGuardrail / runtime failure

Response headers: Cache-Control: no-cache, Connection: keep-alive, X-Accel-Buffering: no. Media type: text/event-stream.

4.6 Inside run_agent() — the choke point

File: src/runner.py. Every interface that wants correct behavior calls this (or stream_agent).

A. _prepare_agent_run

  1. PrivacyGuard.apply_input(question, policy) — block → ValueError; else redacted text as sanitized.
  2. InputGuardrails.validate(sanitized) — length, word count, credential-shaped strings (not a keyword blocklist).
  3. should_use_cache(use_memory, chat_history) — false when cache disabled or memory is on with non-empty history (history would change the answer).
  4. If use_memory and chat_history: effective_question = augment_question_with_history(sanitized, chat_history).
  5. Else: effective_question = sanitized.
  6. Return _Preflight: sanitized (cache key), effective (model input), tracker, cacheable flag.
Why budget is not here
Cost/rate budgets are deliberately not consumed in prepare, so cache hits are free.

B. Cache + budget

  1. If cacheable: get_cached_response(sanitized, mode) → on hit, run _apply_post_guardrails and return (no LLM).
  2. _consume_budget(tracker): check_query_rate + check_token_budget → RateLimitError; then record_query().
  3. _run_with_cost_tracking(effective_question, mode, tracker):
    • reset_llm_provider()
    • Prefer OpenAI callback around _dispatch; Groq fallback estimated if needed
    • _record_spend → tracker + Prometheus

D. Post-processing

  1. _apply_post_guardrails: OutputGuardrails.validate (warn); PrivacyGuard.apply_output (block → ValueError); replace answer.
  2. _finalize_agent_result:
    • If error_code (e.g. node_gate_abort): clear follow-ups, no cache, return.
    • Else optional _maybe_quality_check (only if QUALITY_GUARDRAILS_ENABLED=true).
    • _attach_follow_ups → generate_follow_ups (never fails the request).
    • If cacheable: set_cached_response (serializable fields; not full context_docs).

4.7 stream_agent() differences

  • Prep errors yield {type: "error"} instead of raising through HTTP mapping alone.
  • Cache hit emits synthetic step / answer / follow_ups / sources / done(cached:true) so the UI path is identical.
  • Otherwise: worker + use_emitter(emit); client disconnect sets CancelledRun.
  • During run: steps/tokens via emitter; after: answer → follow_ups → sources → done (+ error_code if abort).

5. Conversation memory (core)

Memory is not a side feature. Follow-up questions (“what about the second approach?”) only work because prior turns are packed into the effective question before any mode runs.

5.1 Two layers

LayerModuleRole
Prompt packing src/memory/chat_memory.py Always available. Compacts history into the question text.
Persistence src/memory/supabase_store.py Optional. Cross-session load/save by session_id.

5.2 Activation gates

  1. Client sends use_memory (default true in API + React).
  2. Server requires settings.memory_enabled (env MEMORY_ENABLED, default true).
  3. _memory_active = use_memory and settings.memory_enabled.
  4. If inactive → history is ignored; no Supabase load/save.

5.3 Resolving history — _resolve_chat_history

  1. If memory inactive → (None, session_id).
  2. Else if client sent chat_history → use it (React local chat store path).
  3. Else if Supabase configured:
    • With session_id → load_messages(session_id)
    • Without → mint a new UUID session id and start empty
  4. Else → (None, session_id) (in-session only via client).

5.4 Compact packing algorithm

Functions: pair_exchanges → format_chat_history → augment_question_with_history.

  1. Pair messages into (user_question, assistant_answer|None) exchanges.
  2. Recent N exchanges (MEMORY_RECENT_EXCHANGES, default 3): keep full question + answer truncated to MEMORY_ANSWER_MAX_CHARS (default 500).
  3. Older exchanges: keep questions only (topic trail), capped by MEMORY_MAX_OLDER_QUERIES (default 10).
  4. Wrap into: 
    Previous conversation:
{history}

Current question: {question}

Instructions:
- If this is a follow-up, use the conversation above for context.
- Prefer recent Q/A pairs for grounding; use earlier questions only for topic continuity.
- If the question stands alone, answer it directly.
Cache interaction
When memory is on and history is non-empty, should_use_cache returns false. Identical questions in different conversations must not share a cached answer.

5.5 Persistence — Supabase

  • Configured when SUPABASE_URL + SUPABASE_KEY are set.
  • save_message(session_id, role, content, mode) inserts into SUPABASE_CHAT_TABLE (default chat_messages).
  • load_messages(session_id, limit=50) returns chronological role/content.
  • Schema: docs/supabase_schema.sql.
  • API persists after a successful answer via _persist_exchange (user then assistant).
  • Streamlit can also persist when configured; otherwise it keeps history in st.session_state.messages.

5.6 Frontend wiring

  • frontend/src/hooks/useChat.ts: useMemory defaults to true.
  • Prior turns from the local chat store are sent as chat_history.
  • sessionId is sent when memory is on so the server can persist if Supabase is available.
  • frontend/src/api/client.ts maps to JSON fields use_memory / chat_history / session_id.

6. The AI agent system (all 7 modes)

Each mode is a different control policy over the same knowledge plane. Node names match the compiled LangGraph graphs in src/graph/. Shared helpers: run_graph_streaming (src/streaming.py) and build_response (src/retrieval/citations.py).

What every mode returns

An AgentResponse: answer, mode, sources, citations, steps, optional route / grade_summary / sub_queries, and follow_ups (attached by the runner).

How to choose a mode

Use baseline/router for speed; crag for quality; decompose/multi_hop for structure; tools for mixed tools; agentic when you want the system to pick.
MODE

6.1 baseline — Fixed pipeline

File: src/rag/baseline.py · Not a LangGraph. Always retrieves, always generates. The control group for every agentic mode.

ask_baseline(question) → retrieve(question) → format_docs(docs) → stream_text(rag_chain, {context, question}) → build_response(mode="baseline", docs=…)

Decisions: none. Use when: simple facts; latency-sensitive; A/B baseline.

MODE

6.2 router — Intent routing

File: src/graph/router_graph.py · Entry: ask_router · Decision: classify_query → direct | retrieve | web_search

START → classify ─┬─ direct ─────────→ direct_answer → END ├─ retrieve ──→ retrieve → generate → END └─ web_search → web_search ──────────→ END Nodes: classify_node → RouteType via structured output direct_answer_node → direct_chain retrieve_node → retrieve() generate_node → rag_chain web_search_node → DuckDuckGo + web_search_chain

Gap vs CRAG/agentic: no document grading, no node_gate abort path.

Use when: greetings should skip retrieval; newsy questions need the web.

MODE

6.3 crag — Corrective RAG

File: src/graph/crag_graph.py · Adds a grader loop after retrieval. Largest quality jump over baseline.

After gradegrade_condition: docs → generate; else rewrite or web_fallback

Use when: answer quality matters and you can afford grading latency.

MODE

6.4 decompose — Parallel sub-queries

File: src/graph/decompose_graph.py · Map-reduce via LangGraph Send to retrieve_sub workers.

START → classify ─┬─ direct → direct_answer → END ├─ web → web_search → END └─ retrieve path → decompose │ ├─ Send(sub_q1) → retrieve_sub ─┐ ├─ Send(sub_q2) → retrieve_sub ─┼→ synthesize → END └─ Send(sub_qN) → retrieve_sub ─┘ Nodes: decompose_node → decompose_query → sub_queries fan_out_to_retrieve → Send per sub-query retrieve_sub_node → retrieve for one sub-query synthesize_node → synthesis_chain

Use when: “Compare X vs Y vs Z”, multi-entity questions known upfront.

MODE

6.5 multi_hop — Sequential reasoning

File: src/graph/multi_hop_graph.py · Unlike decompose, hop N+1 depends on findings from hop N.

START → classify ─┬─ direct → direct_answer → END ├─ web → web_search → END └─ analyze → retrieve_hop → reflect ─┬─ sufficient → synthesize → END └─ next hop (until MAX_MULTI_HOP_STEPS) Helpers: analyze_question, reflect_on_hop (src/agents/multi_hop.py) reflect_condition: sufficient OR (not multi-hop and hop≥1) OR hop ≥ max → synthesize else → retrieve_hop

Use when: “What fallback does CRAG use when retrieval fails?” — must learn CRAG first.

MODE

6.6 tools — Tool-calling agent

File: src/graph/tools_graph.py · Node tools_agent runs an internal loop (≤10 turns) with llm.bind_tools(TOOLS).

START → classify ─┬─ direct → direct_answer → END ├─ web → web_search → END └─ tools_agent ⟲ (tool_calls) → END abort → END TOOLS (src/tools/all_tools.py): • retrieve_docs(query) → vector corpus • web_search(query) → DuckDuckGo (circuit-breaker wrapped) • calculator(expr) → AST-restricted arithmetic (no eval()) check_tool_result quarantines bad outputs; abort after MAX_TOOL_FAILURES (3).

Use when: mixed modalities — math + corpus, or dynamic tool choice.

MODE

6.7 agentic — Full orchestrator (default)

File: src/graph/agent_graph.py · Entry: ask_agentic → build_full_agent_graph. Combines routing, strategy selection, the four retrieval strategies, and a CRAG-style grade/rewrite/fallback safety net on every retrieval path.

Important implementation details
  • Strategy nodes reuse Phase 4–6 graphs with skip_router=True; nested token emission is suppressed so the outer graph owns the streamed final answer.
  • After rewrite, the edge is rewrite → grade (rewrite re-retrieves internally). This differs from standalone CRAG, where rewrite loops back to a named retrieve node.
  • Tools with empty graded docs but a prior tool answer: grade_condition routes to generate to keep that answer instead of forcing web fallback.
  • Strategy prompt lives in src/agents/orchestrator.py (STRATEGY_PROMPT), not src/prompts.py.

9. Generation, citations, follow-ups, streaming

9.1 Generation chains

LCEL chains in src/chains/generation.py: rag_chain, direct_chain, synthesis_chain, web_search_chain. Pattern: prompt | get_llm() | StrOutputParser.

9.2 LLM client — src/llm.py

  • Primary: OpenAI ChatOpenAI with hard timeout, max_retries, max_tokens.
  • Fallback: if LLM_FALLBACK_ENABLED and GROQ_API_KEY are set, FallbackChatModel wraps both providers with with_fallbacks, and mirrors with_structured_output / bind_tools.
  • reset_llm_provider / get_llm_provider ContextVars attribute spend correctly when fallback fires.

9.3 Citations — src/retrieval/citations.py

Builds Citation objects (src/schemas.py): index, chunk_id, source, page, section, snippet, score. Helpers: docs_to_citations, docs_to_sources, docs_to_context, build_response.

9.4 Follow-ups — src/agents/followups.py

After every successful (non-abort) run, generate_follow_ups proposes up to three questions grounded in retrieved snippets (or the answer text as fallback). Failures are swallowed so follow-up generation never fails a query.

9.5 Streaming internals — src/streaming.py

  • use_emitter / emit_step / emit_token — ContextVar-based event bus.
  • stream_text / stream_llm_message — token streaming for final answers.
  • run_graph_streaming(graph, initial_state) — stream_mode="values"; emits new steps as nodes complete.
  • suppress_token_emit — used inside nested strategy subgraphs that regenerate later.
  • CancelledRun — raised when the API cancels a stream on disconnect/timeout.

9.6 Schemas — src/schemas.py

Public response shape is AgentResponse (includes error_code). Agent structured models (RouteDecision, DocumentGrade, StrategyChoice, etc.) live near their agents.

Multi-worker rule
Before raising API_WORKERS above 1, run Redis and set RATE_LIMIT_BACKEND=redis (compose already does). In-memory limits are per-process and under-count under load balancing. Production validation refuses to boot otherwise.

16. Worked traces

Re-run these with -v to see steps fill in live.

16.1 Simple fact — baseline vs crag

python -m src.cli ask "What is Self-RAG?" --mode baseline -v
python -m src.cli ask "What is Self-RAG?" --mode crag -v
What to notice
Baseline: one retrieve → generate. CRAG: retrieve → grade each chunk → maybe rewrite → generate (or web fallback if the corpus is weak).

16.2 Comparison — decompose

python -m src.cli ask "Compare naive RAG, advanced RAG, and modular RAG" --mode decompose -v
What to notice
sub_queries appear; parallel retrieve_sub workers; one synthesis.

16.3 Sequential dependence — multi_hop

python -m src.cli ask "What fallback does CRAG use when retrieval fails?" --mode multi_hop -v
What to notice
Hop 1 finds CRAG; reflect builds hop 2 query about fallback; synthesize.

16.4 Full orchestrator — agentic

python -m src.cli ask "Compare RAG vs Agentic RAG; what is Self-RAG grading?" --mode agentic -v
What to notice
Steps show Router → retrieve, then Strategy: decompose|…, then grade, then generate. Same question through baseline will be shallower.

16.5 Memory follow-up (API)

curl -s -X POST http://localhost:8000/query \
  -H "Content-Type: application/json" \
  -d '{
    "question": "What about the second approach?",
    "mode": "agentic",
    "use_memory": true,
    "chat_history": [
      {"role":"user","content":"Compare naive and advanced RAG"},
      {"role":"assistant","content":"Naive RAG retrieves once… Advanced RAG adds rewriting…"}
    ]
  }' | jq '.answer,.steps'
What to notice
Without history, “the second approach” is ambiguous. With memory packing, the runner injects prior Q/A so the agent resolves “second” to advanced RAG.
